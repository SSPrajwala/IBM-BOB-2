We used IBM Bob 2.0 as the builder for the entire project, across two iterations, not just a code-completion assistant. The build ran in an agent-mode session with full file, shell, and document-understanding access, and the deliverable is itself a multi-agent system, so Bob was effectively used to build a smaller version of itself.

**Iteration one** scaffolded TaskFlow API, a seeded FastAPI demo with realistic defects (an f-string SQL query, two unchecked-lookup bugs, a dependency with a known unsafe-load advisory, 20% test coverage), and DevPilot's first four subagents — onboarding, code review, testing, release readiness — run in parallel via a thread pool. Bob wrote each subagent as an independent module, then debugged real failures by reading tracebacks rather than guessing: a malformed regex list, and a SQLite disk-I/O error traced to the sandbox's mounted filesystem rather than the app.

**Iteration two** came from feedback that the prototype needed to prove generality, not just work on its own demo. Bob refactored all four subagents off TaskFlow-specific assumptions into a shared repo-scanning module, added an app-entrypoint detector so generated tests import the real app automatically, and fixed two regressions this surfaced (a route-prefix bug silently zeroing out coverage, and a false null-check match against a code comment containing "404") by reproducing each one and reading the AST output directly rather than assuming a fix worked. It then proved generality by shallow-cloning a real, unmodified public repo (miguelgrinberg/microblog, a Flask app) live from GitHub and running the pipeline against it cold.

On feedback that findings needed to be trustworthy and role-appropriate, Bob added: cross-agent corroboration (a static finding is "confirmed" only when a generated test independently fails against the running app — verified live: two TaskFlow findings confirmed, zero false positives on microblog); a fifth subagent for legacy modernization; a sixth for auto-fix, which parameterizes the SQL query, adds the missing null checks, bumps the flagged dependency, re-runs the real test suite (10/10 passed), and commits locally — pushing and opening a PR is a separate script requiring the user's own GitHub token and an explicit `--confirm` flag, never automatic; role-scoped dashboard views; and an "Ask DevPilot" layer wired to a real watsonx.ai REST client (IAM token exchange, text-generation endpoint) built from IBM's current docs, with a deterministic fallback so the demo never depends on credits the team doesn't have yet.

**Verification throughout.** Every claim here was checked by running the actual code: docx/pptx outputs were rendered to images and inspected page-by-page; the auto-fix diff was read line-by-line before being called "clean"; the confirmed-findings count came from parsing real JSON output, not memory.

Net effect: two sessions took this from a blank brief to a generalized, self-verifying, cross-checked prototype proven on a real GitHub repo, plus its supporting documents, with no tools outside Bob involved. watsonx Orchestrate was deliberately not force-integrated (its 30-day trial is UI-driven, a poor fit here); that tradeoff is documented, not hidden.
